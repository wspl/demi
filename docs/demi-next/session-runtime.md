# Demi Next：会话架构提案

状态：待评审，未实现。本文只讨论三个架构决策；现行约束仍以 `docs/package-boundaries.md` 为准。

**目标：每个 agent 使用同一套运行机制，状态归属明确，进程中断后不会凭猜测重复执行。**

## 决策一：Agent 同构，父子关系只决定组织与策略

**问题。** 根会话与子代理分别装配工具、执行环境、事件和销毁流程。同一种能力需要维护两条路径，行为容易分叉。

**方案。** 所有 agent 使用同一个创建/恢复入口、状态机、存储契约和事件协议。父子关系用 `parentId` 表达，根节点的 `parentId` 为空。

```text
conversation c1
  a1  parentId=null ─┐
  a2  parentId=a1   ─┼── 同一装配入口 ── 同一种会话运行时
  a3  parentId=a2   ─┘                    每节点独立的状态和资源
```

提示词、模型、命令集合和完成策略可以不同。例如“完成后关闭”是一项任意节点都能使用的策略，不是子代理专属生命周期。关系模块负责委派、消息和结果交付，不另外构造运行时。

**为什么。** 父子关系不改变推理、工具或持久化的本质；把差异放进配置，可以让这些机制只实现一次。

**检验。** 给任意节点配置相同策略，把它放在根、子、孙三个位置，同一套创建、恢复、事件和销毁测试都应通过。若新增能力仍需分别修改根和子代理实现，同构就没有成立。

## 决策二：状态属于会话，Host 只负责执行

**问题。** `Host.store` 承载会话状态，但 Host 又是可切换的执行目标；恢复状态因此依赖先取得 Host。根和子代理的 checkpoint 原子性也不同。

**方案。** 会话存储独立注入。区分 conversation 的范围、agent 身份和执行目标：

```text
c1 的数据库：保存 a1、a2、a3，各节点使用同形数据和同一存储实现
                       │
                       └── a3 新建执行 e7 ── 固定到 Host A
                              新执行可切到 Host B
                              e7 的查询/输入/取消仍找 A
```

节点按稳定 ID 存储，父子关系不编码进存储路径。Host 负责文件和进程；命令状态也按会话注入，切换 Host 不改变其归属。旧执行仍要检查当前授权。

存储必须提供三项原子保证：

| 操作 | 必须一起提交 |
|---|---|
| 创建节点 | 节点、父关系、初始状态和第一条消息 |
| 保存会话 | transcript 变更、状态和消息消费进度 |
| 完成节点 | 最终状态、结果和需要交付的完成消息 |

Backend 继续使用每 conversation 一份 SQLite，利用本地事务完成这些操作。流式文本允许合并落盘；消息接受、执行派发和完成确认必须等待相应提交成功。

**为什么。** 会话可以跨执行目标持续存在；它的身份、存储和恢复保证应保持稳定。完成消息一起提交，才能避免“任务已经完成，父节点却永远没收到结果”。

**代价。** 存储接口需要表达原子提交，逐 key 写 JSON 不再满足完整的持久化契约。

**检验。** Host 离线时仍可读取会话。切换 Host 后状态不变。保存或完成过程中强制退出，重启只能看到完整的旧提交或新提交，不能混合，也不能丢失已确认的消息。

## 决策三：按执行证据恢复，未知结果不自动重放

**问题。** 命令可能已经产生效果，但 backend 没收到或没保存结果。把这种情况当成普通失败重试，会重复执行。

**方案。** 为实际操作保存独立执行记录，包含稳定 operationId、目标、恢复所需输入和已知结果。工具调用关联该记录：`shell_exec` 返回 running 时，工具调用已结束，实际命令仍在运行。

```text
a3 执行 e7
  持久化派发标记 ── 调用 Host A ── 持久化结果 ── 推进会话
                         ↑
                    此处断线或进程退出
                    恢复先查询 e7 的证据
```

| 恢复时的证据 | 行为 |
|---|---|
| 能证明尚未开始 | 可以进行第一次执行 |
| 确认仍在运行 | 继续观察原执行 |
| 有最终结果 | 使用已有结果 |
| 无法确定 | 保留 `unknown`，不自动重放 |

执行记录不依赖可能被上下文压缩移除的 transcript。取消请求与确认退出分别记录；断线不等于失败，非零退出也不代表没有部分效果。

**为什么。** 本地事务不能包住任意外部命令。受控操作只有把业务变更、去重和回执放进同一事务，才能保证重复请求不会重复生效；任意 shell 和 stdin 写入必须保留不确定性。

**代价与保证边界。** 无证据时宁可暂停自动恢复，也不冒险重放；派发标记写完但实际尚未发送就退出，也可能落入 unknown。该方案保证框架不盲目重放，不承诺所有外部效果只发生一次。

**检验。** 模拟“操作已生效，结果未保存”后退出。重启必须查询回执或报告 unknown；如果直接重新执行，即为设计失败。

## 评审只需判断这三件事

1. 父子关系是否有理由需要第二种运行时？本方案认为没有。
2. 会话存储是否应随执行机器改变？本方案认为不应，并要求所有节点获得同样的原子提交保证。
3. 无法确认外部操作结果时，能否自动重放？本方案认为不能，必须保留未知状态。

这三个边界确定后再细化类型、表结构和实现步骤。验收分别落在 agent 的节点契约测试、backend 的存储故障测试、agent/shell 的执行恢复测试；使用受控 provider，不调用真实模型。
