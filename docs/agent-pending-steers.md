# Reading pending user steers

A steer is a message supplied while a turn is running, such as “leave the cookie
helper unchanged.” When a provider cannot accept the message immediately,
`AgentSession` holds it until the next sampling or tool boundary. A **pending
steer** is an accepted message that has not yet been written to the transcript.
It is separate from a queued message, which starts another turn.

## Framework responsibilities

`AgentSession.pendingSteers()` returns a detached copy of the accepted user
steers still waiting to enter the transcript. The `PendingSteer` type in
`@demicodes/core` contains:

| Field | Meaning |
| --- | --- |
| `id` | The message ID supplied to `steer`, or generated by Demi. The transcript uses the same ID. |
| `turnId` | The active turn receiving the message. |
| `model` | The model selection recorded when the message was accepted. |
| `content` | The resolved user content, including any attachments. |

The list excludes internal wakeups and structured agent messages. Returned objects and attachment
bytes are copies; changing them does not change the session's queue.

`AgentSession` publishes `pending_steers_changed` with the complete public list
when a user steer is added, canceled, written to the transcript, or discarded.
A provider that accepts a steer directly writes it to the transcript without
adding a pending item.

`AgentServer` sends a `pending_steers` frame when a client opens a session, after
the initial transcript, phase, and queued-message frames. It then forwards the
session's list changes through the same frame type:

```ts
{ type: 'pending_steers', pendingSteers: PendingSteer[] }
```

`AgentClient` validates this frame, keeps the current list, and exposes it through
`pendingSteers()` and subscription events of type `pending_steers`. Its getter
returns detached copies. As transcript updates arrive, the client removes pending
items whose IDs already appear in steer blocks. Equal message text does not mean
equal messages: each ID is handled separately. Closing or replacing the client's
session clears its pending list.

The existing `steer_result` frame acknowledges a send operation. It does not
replace the list notification. `AgentClient.cancelPendingSteer(id)` remains a
fire-and-forget cancellation request; callers observe the resulting list and
transcript rather than interpreting the method's return as confirmation.

## Connecting again to a running session

Suppose `AgentSession` has accepted message S1 but has not yet written it to the
transcript. A new `AgentClient` opens the same session ID while that session is
still running. `AgentServer` attaches the new client to the existing session and
returns S1 in the initial pending list. It does not send S1 to the model again.
When S1 enters the transcript, the client no longer reports it as pending.

`AgentClient.open()` resolves on the `opened` frame, as before. The initial data
frames follow it; subscribe to `pending_steers` to observe receipt of the list,
including an empty list.

This behavior applies to a client reconnecting to an existing in-memory session.
Human pending steers are not included in the persisted session checkpoint.
A newly loaded session does not recover those human inputs. Agent-originated
records in the same queue are persisted as `pendingInternalSteers`, under the
[agent-message contract](agent-messages.md), and remain excluded from the human list.

## Product integration

The framework owns the queue and its notifications. A product backend does not
need a second store of pending steers for reconnecting clients. A UI can render
`AgentClient`'s list and match transcript messages by ID. Browser refresh is one
reason to create a new client; the framework behavior also applies to non-browser
callers.

The current Web UI's local optimistic steer handling is a separate consumer and
must be connected to these notifications during product integration. Adding the
framework API alone does not update that UI behavior.
