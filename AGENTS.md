# Working Principles

- The system serves the interface, and the interface serves the user; never the reverse. Design the interaction first, by the principle of least astonishment and the industry's consensus, with a precedent in mainstream software (browsers, Finder, macOS's own apps); then design the system to deliver it. An interaction that follows from what the mechanism makes easy, or that no mainstream software has, is wrong however correct its mechanism is.
- Create first, then edit. An Add action creates the thing at once, with a default for every field (a name such as *Compatible API*, *Compatible API (2)* for the second), and opens the same editor an existing one opens; nothing asks for a value in a dialog before the thing exists, as Finder's New Folder and Mail's Add Account do not. Adding and editing are one view, with the same fields in the same order, and every field stays editable afterwards unless the thing's nature fixes it. A field the thing cannot work without is shown as missing, never demanded up front; a field it can work without is optional.
- Be pragmatic, never formalistic. Every step either moves the work forward or protects its correctness; drop ceremony that does neither, such as a check that cannot fail on the change at hand, a repeated full suite, or a report nobody needs.
- Tests follow [Testing](docs/delivery/testing.md). In short: each test protects a behavior a user or another component relies on, or a fixed bug, at the boundary where it is observable, once, with scenarios first; it fails before the fix or with the planted defect; it waits for events, never for time; it stays within its time budget and states its cost; it never restates the implementation or asserts a defect as correct. A test you touch that breaks these rules is fixed or deleted then.
- Follow the boy scout rule for defects only: what you notice that fails, is wrong, slow or unreliable, or breaks a written design or rule, fix then, and say what you changed and why in the commit message, where the next session reads it. What the product does, shows and says changes only by the user's request or a design the user agreed. Stop and ask only about what changes the agreed design or scope, cannot be undone, or reaches beyond the repository and its build products.
- Read the code that does the thing, and its module's entry comment, before discussing a change: the code is the authority on what Demi does.
- Single source of truth: one owner per fact and per purpose; two implementations of the same one-sentence purpose are a defect regardless of length or package. No stored value that can be derived; mutually exclusive phases are one status, never several flags.
- A change is announced by whoever owns the fact, when it happens; nobody else finds it out by asking. Never poll a Host, a service or a store for whether something changed, and never re-read on an unrelated event (a job's end, a timer, a reconnect) in the hope of catching a change. When the owner has no way to announce it yet, build that channel first; reading on a proxy event in the meantime is a defect, not a fallback.
- The conversation's side of the page asks only the backend, never a Host through it. What it shows from a Host, such as a directory's instruction files or workflows, the backend keeps: the runner watches exactly what each fact depends on and reports a change, the backend reads the fact again, stores it with when it was read and announces a new value, and a request takes what is held, without waiting on or waking a Host (`crates/backend-host-access/src/kept.rs`). The work panel, which shows a Host's own files and changes, reads the Host when shown.
- Every timer, listener, stream or worker is released on success, failure and cancellation. An ignored error says why it is safe to ignore.
- Implement the intended final design. Do not add compatibility layers or legacy-data migration, cleanup, or normalization paths. The one exception is the schema migrations, which `crates/backend-database/src/lib.rs` (§ Schemas and migrations) requires: the first change to a database schema after a release or a deploy adds the schema that release or deploy shipped to the history with its migration, and a later change before the next one extends that migration instead of adding another ([A development build on a server](docs/delivery/upgrades.md#a-development-build-on-a-server)).
- Correct a model's behavior (a system prompt, an instruction, a tool's description) with the general rule it missed, never by writing the case at hand or its answer into the text: a prompt that quotes the incident it was fixed for teaches that incident and nothing else, and every such patch makes the prompt longer and worse. Before changing the text, state the rule in one sentence without the incident's details, check that it holds for cases other than the one seen, and leave the incident to the commit message.
- Do not write a script or a tool for a task that can be said in a sentence and done by hand or by an agent following it; a tool is for what is done often and the same way each time.
- Before writing a helper whose purpose does not mention this project's domain, search the standard library, the crate's declared dependencies and the workspace, in that order (in the frontend: the package's declared dependencies, `@demicodes/utils`, and the workspace). Write it only when the search fails, where the next caller will find it.
- Use a library from its installed types and documentation, not from memory. Any cast (`as unknown as`, `any` or a type-only import in TypeScript; `unsafe`, `transmute` or a downcast in Rust) used to get around a library's types means you do not know its API: stop and read it. If the library genuinely lacks the capability, say so in a comment at the workaround.
- When a library is adopted for a job, use the whole of it for that job. Using it for one step and hand-writing the adjacent step it also covers (its coercion, its introspection, its error reporting) is a defect.
- Parse, don't validate: a value from outside the process is decoded against a schema at the point of entry, its type derived from the schema, never asserted. Corrupt data is never silently repaired.
- Prefer protocols, APIs, and file interfaces over external CLI processes.
- Run checks appropriate to the change. An automated test never calls a real
  model: it works against fixtures or stubs, so a suite costs nothing and
  answers the same way every time. Accepting a change by using the running
  product is a different thing, and there sending a real message is part of
  the check; stop a turn once it has shown what you were looking for.
- Every reusable UI behavior lives in `web-ui` as a component or primitive, and a plugin's feature UI lives in its plugin package, written only against `@demicodes/plugin-sdk` (`packages/plugin-sdk/src/index.ts`); `web-ui` knows no plugin, and `web` and `web-gallery` supply only data, state, services and handlers. A behavior first built for one surface (a control's affordance, a page's interaction, a dialog flow) is generalized into `web-ui` before the checkpoint, never left local to the gallery, the product or one plugin.
- Keep `web` and `web-gallery` synchronized in both directions. Every UI change is made once, in `web-ui` or in the plugin package that owns it, whether the request came from the gallery or the product, and lands in both surfaces in the same checkpoint: update the gallery specimens and the product usage together, and verify the result in both. A change visible in only one of them is incomplete.
- Every control in the gallery responds when used. A specimen's button, menu item or link either acts on the specimen's own state the way the product would (Cancel drops the row, Clear empties the list, a dialog's buttons close it and a control opens it again), or simulates what the product would do with a host or another page and says so, for example in a neutral toast naming the action. A click that does nothing is a defect, in a specimen that shows a pinned state or a look as much as in a live one. Bind every event a specimen's component emits, and click through each new specimen before the checkpoint.
- Everything committed, code, comments, documents, tests, fixtures, gallery data and commit messages alike, holds only invented examples: made-up tasks and titles, names such as *alex*, domains such as `example.com`, paths such as `/Users/alex`. Nothing committed comes from a real development session or environment: no conversation's title or words, no account of who asked for a change or how it was discussed, no real person's, account's, machine's, host's or server's name, no real path, address or secret.
- Write code comments in English.
- Write separate steps on separate lines.
- Before committing, reread the complete functions you changed, not just the added lines. Check for repeated conditions, duplicate or unused values, ignored errors, and code in the wrong package. Fix those problems before calling the work complete, even when tests pass.
- Whether a change is accepted by using the product, and by whom, is decided for each change by whoever leads the work. An acceptance starts its processes from the new code once, after the whole change is complete, and stops the processes it started when it is done.
- Stop only the processes you started, by the process id or server id you recorded when you started them, never by a name or a pattern (`pkill -f`, `killall`): the user's own development backend runs the same programs.
- Product and gallery checks drive the browser with `bun browse` ([Product checks](docs/delivery/browse.md)), a whole check as one short Playwright script in one call, not a shell call per step. The tool is everyone's to change: a check that needs what it lacks adds it, and a command that misleads or breaks is fixed then, never worked around with a one-off script.
- A product check that needs something the development setup lacks, such as a paired device, a runner, a browser on a Host or a model's reply, sets it up and runs: pair a runner to the development backend through Add Device, install what the Host needs, send the real message. A check skipped because the setup lacked it is not a pass, and a gallery check never stands in for the product's. Remove what was set up only for the check once it is done.
- A screenshot is reviewed, not only taken. Whoever takes or sends one looks at everything on it, not only the change it was taken for, and fixes on the spot only the defects it shows, as the boy scout rule defines them; the lead does so for every screenshot before it reaches the user, and hands what it finds to the work in progress.
- Any change whose effect can be seen on screen is accepted with screenshots, not only a change of style: a layout, an interaction, a state, a flow, a message, a fixed bug. The self-check takes one screenshot of each screen the change affects, showing the change in effect, and the report puts them in front of the user, one image per screen. A subagent saves its screenshots outside the repository and lists their paths in its report; the lead sends them to the user.
- The Cloud and a paired device are the same thing: a Host behind a runner. Code never distinguishes them except where the design says they differ (pairing, revocation, lifecycle). Anything that reaches a conversation's Host goes through the conversation's host access (`with_host` in `backend-host-access`, see `crates/backend-host-access/src/lib.rs`), which resolves the target, wakes a stopped Cloud, and holds the file gate. There is no other way to a conversation's Host, and every other way to a Host is named in that comment; if the host access does not fit, change it first.
- In development, build native code with the machine's own toolchain and cross tools, not the build container, and build and package only the targets of the Hosts in use (`crates/xtask/src/main.rs`). All six targets are for a published release, which the release workflow builds on GitHub's hosted runners, each platform on its own (`.github/workflows/release.yml`).
- A work package is one change a user or a reviewer understands on its own, such as "a device is drawn as its system's logo" or "a Claude Code answer that replaces a failed stream is handed on": its decision record when it makes a new decision, its code and its tests together. It is one commit with a Conventional Commit subject that says what changed and why, pushed once; a later fix to it before it lands, a review's rework or a reworded sentence of its decision record included, is folded into that commit (`git commit --amend`), never added as a commit of its own. A commit never holds a part of a work package, such as its runner half or its decision record alone.
- Release only when the user asks for a release; releasing and upgrading the user's server then need no further confirmation. Deploy to the server `DEMI_DEPLOY_HOST` names in the user's `.env` with `bun xtask deploy` (`docs/delivery/upgrades.md` § A development build on a server) only when the user asks for it, each time, and then the whole merged batch.

# Building and Testing

- The full typecheck and test suites run once, when a work package is delivered, never between edits. A small change the lead makes itself (`.demi/workflows/parallel.yaml`) runs neither: the CI's checks cover it. When it changes a test, only that module's tests run.
- Build and test with one Cargo selection everywhere: `cargo check --workspace --all-targets --features demi-runner/test-fixtures` and `cargo test --workspace --features demi-runner/test-fixtures`, adding `--test <name>` for one target. Never `-p <crate>` for a test build: each selection keeps its own copy of the dependencies, and switching has cost 140 s a time.
- Keep test binaries few: each crate has one (`ARCHITECTURE.md` § Test binaries), such as `crates/runner/tests/runner/` and `crates/plugin-browser/command/tests/browser/`, and the crate boundary check enforces it; a test gets a binary of its own only when it changes or saturates process-wide state. Each binary costs a link and, when newly built, a first-launch check of about three seconds here. TypeScript tests never build a program: `bun run test` builds them and runs the suite in parallel; to run some tests, build first and set `DEMI_TEST_PROGRAMS=target/debug`.
- Do not run `cargo fmt` or `cargo clippy`, and do not add them to any check: neither is part of this project's validation.
- The compiler is the only hard constraint on how code and text are written. A convention (naming, capitalization, layout, style) is written down in `ARCHITECTURE.md`, an entry comment or the gallery and followed; never enforce one with a lint, a script or a test. Tests protect behavior.
- Work in large steps: read what a step needs in one call, write the whole step, then compile once. Start long builds and tests in the background and keep working meanwhile.
- zsh does not split an unquoted variable into words; pass argument lists as arrays, or run scripts with bash.

# Writing and Communication

- Make the first explanation understandable without requiring the reader to ask for a simpler version. Start with what happens in a concrete example, then explain the rule. Use familiar words; introduce a technical term only when needed and explain it on first use.
- When identifying a problem or ambiguity, show the exact situation, what each rule would make happen, and why the difference matters. Do not substitute abstract labels such as "content missing" or "rules overlap" for that explanation.
- Before sending an explanation, check whether the reader can tell who does what, to which thing, and with what result. Rewrite sentences that require the reader to translate terminology or infer omitted steps. Keep necessary technical detail; remove detail that does not help answer the question.
- Prefer diagrams for structures, relationships, and flows when they clarify the explanation; use ASCII diagrams when practical. Labels must be understandable from the accompanying explanation.
- Explain responsibilities, boundaries, observable behavior, and design rationale. Leave implementation details that code can express clearly to code.
- Distinguish verified facts, suspected problems, proposals, and open decisions.
- UI text follows macOS capitalization: the gallery's Writing page (`packages/web-gallery/src/sections/WritingSection.vue`) is the rule.
- UI text, in English and in every language Demi speaks, is chosen by comparing many products that say the same thing well, never by one source or a fixed rule: AI apps of the same kind (Codex, ChatGPT, Claude), the system's own apps (macOS, iOS), and developer tools such as VS Code only for developer concepts ([Localization](docs/product/localization.md)). Take what a user of that language reads without stopping; when the products differ, judge which is best and say why in the glossary. English is decided first; every other language says what the English says.
- Every document, decision record and comment must follow the [Google developer documentation style guide](https://developers.google.com/style), and its Markdown the [Google Markdown style guide](https://google.github.io/styleguide/docguide/style.html). Use Diátaxis, arc42, and C4 as optional aids to clarity and completeness, not as mandatory directories, sections, or deliverables.
- Doc comments must also follow their language's conventions: in Rust, [RFC 505](https://rust-lang.github.io/rfcs/0505-api-comment-conventions.html), [RFC 1574](https://rust-lang.github.io/rfcs/1574-more-api-documentation-conventions.html) and the rustdoc book's [How to write documentation](https://doc.rust-lang.org/rustdoc/how-to-write-documentation.html); in TypeScript and JavaScript, the comment sections of the Google TypeScript and JavaScript style guides; in shell, the Google Shell Style Guide's comment section; in Python, [PEP 257](https://peps.python.org/pep-0257/).

# Design Documentation

- The code is the only authority on what Demi does and how. Whatever code can say, a type, a name, a test, the code says; a comment says only what the code cannot: a module's purpose and boundaries, an invariant, the reason for a non-obvious choice and the alternative it refused. A comment that restates what the code does is deleted.
- A module's design lives in its entry comment (`lib.rs`, `main.rs`, `index.ts`), next to the code it describes, with an ASCII diagram of at most 80 columns where a structure or a flow is clearer drawn. `ARCHITECTURE.md` holds only the map and the rules that hold across modules, and the dependency graphs.
- Product behavior, what the user sees and does, lives in the gallery and in the tests that protect it, never in prose.
- A new decision, one that changes what the user sees, a protocol or a module's boundaries, is written as a decision record (ADR) before it is built: `docs/decisions/NNNN-name.md`, numbered in order, following the minimal template of [MADR](https://adr.github.io/madr/). A decision that changes what the user sees draws the expected screen as an ASCII sketch. It leaves out fields, constants and steps, which the code holds. The lead shows it to the user, and it lands in its work package's commit. A merged decision record is never edited, except for its status; a later change is a new record that names the one it supersedes.
- A bug fix makes no new decision and needs no decision record: its commit message says the symptom, the cause and the fix, and it adds a test that fails before the fix.
- `docs/` holds only what is not about one module: the overview, the comparison, guides, operator steps (setup, installation, upgrades), testing, product checks, the localization glossary, the decision records and the brand's assets.
